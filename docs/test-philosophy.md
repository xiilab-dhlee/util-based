# Test Philosophy for AI Agent

> Based on Kent C. Dodds – "How to Know What to Test"

## 문서의 목적

이 문서는 AI 에이전트가 테스트 코드를 생성하기 전에 **"무엇을 테스트할지"** 판단하도록 돕기 위한 철학 문서입니다.

### 이 문서의 목표는:

- **테스트 개수를 늘리는 것이 아닙니다**
- **코드 커버리지를 높이는 것이 아닙니다**
- **사용자 관점에서 신뢰할 수 있는 소프트웨어라는 확신(confidence)을 얻는 것**입니다

---

## 테스트의 본질적 목표

테스트는 코드가 존재한다는 사실을 증명하기 위한 도구가 아닙니다.

테스트의 목적은 **"이 소프트웨어가 실제 사용 시 기대한 대로 동작한다는 신뢰를 주는 것"**입니다.

따라서 테스트는:

- 내부 구현(함수, 상태, DOM 구조)
- 기술적 세부사항

이 아니라, **사용자가 경험하는 결과와 행동을 검증**해야 합니다.

---

## 무엇을 테스트해야 하는가 (Use Case 중심 사고)

### 테스트 대상은 "코드"가 아니다

AI 에이전트는 다음 질문부터 스스로에게 해야 합니다:

> "이 코드는 어떤 상황에서, 누가, 왜 사용하는가?"

테스트는 **use case (사용 사례)** 단위로 작성합니다.

### 좋은 테스트의 기준 질문

테스트를 생성하기 전, 반드시 아래 질문에 답해야 합니다:

1. **이 기능이 깨지면 사용자가 실제로 불편한가?**
2. **사용자가 직접 인지할 수 있는 변화인가?**
3. **이 테스트가 실패하면 행동을 바꿔야 할 의사결정이 생기는가?**

위 질문 중 하나라도 "예"라면 테스트 가치가 있습니다.

---

## 테스트 레벨 선택 원칙

AI 에이전트는 모든 검증을 E2E로 작성하려 해서는 안 됩니다.

### 코드 커버리지는 목표가 아니다

- 코드가 실행됐다는 사실 ≠ 중요한 기능이 테스트됐다는 뜻
- 커버리지는 참고 지표일 뿐, 성공 기준이 아닙니다

### 테스트 피라미드 원칙

| 테스트 레벨 | 목적 |
|------------|------|
| Unit | 로직의 정확성 |
| Integration | 컴포넌트/모듈 간 협력 |
| E2E | 사용자 핵심 흐름에 대한 신뢰 |

**E2E 테스트는 가장 적고, 가장 중요해야 합니다.**

---

## E2E 테스트 작성 원칙 (AI 필수 규칙)

AI 에이전트는 E2E 테스트를 작성할 때 다음 규칙을 **절대적으로** 따릅니다.

### 1. 사용자 관점만 검증한다

**금지 (구현 세부사항 테스트):**

- DOM 구조
- CSS 클래스
- 내부 상태
- private 함수

**허용:**

- 버튼 클릭
- 텍스트 입력
- 화면 전환
- 사용자에게 보이는 결과

### 2. "무엇을" 테스트하고 "어떻게"는 테스트하지 않는다

- **Bad:** "이 컴포넌트는 useEffect를 사용한다"
- **Good:** "사용자가 버튼을 누르면 결과가 나타난다"

### 3. 상태 기반 대기만 사용한다

AI는 절대 다음을 생성하지 않습니다:

```typescript
// 금지
waitForTimeout()
sleep()
```

대신 반드시 **상태 변화를 기다립니다:**

- URL 변경
- 요소 표시/비표시
- 텍스트 등장

---

## E2E로 하면 안 되는 것들

아래 항목은 E2E 테스트 대상이 아닙니다:

- enum 값의 유효성 검증
- 단순 렌더링 여부
- API 계약 검증
- 스타일 세부 사항
- 단순 조건 분기 로직

이런 검증은 **unit / integration / contract test**로 작성합니다.

---

## 좋은 테스트의 이상적인 모습

좋은 테스트는 다음 특징을 가집니다:

- 읽으면 시스템의 사용법이 이해된다
- 리팩토링에 잘 깨지지 않는다
- 사용자의 행동 시나리오와 1:1 대응된다
- 내부 구현 변경으로 실패하지 않는다

---

## AI 에이전트 최종 지침

AI 에이전트는 테스트 코드를 생성하기 전에 반드시 다음을 수행합니다:

1. **사용자 시나리오를 자연어로 먼저 정의한다**
2. **그 시나리오가 깨질 때의 사용자 영향을 평가한다**
3. **테스트 레벨(Unit / Integration / E2E)을 선택한다**
4. **가장 낮은 비용으로 가장 높은 신뢰를 주는 테스트를 선택한다**
5. **그 이후에만 코드 생성을 시작한다**

---

## 핵심 문장

> "The more your tests resemble the way your software is used, the more confidence they can give you."
>
> — Kent C. Dodds

---

## AI 테스트 생성 금지 항목

AI 에이전트는 다음과 같은 테스트를 자동 생성해서는 **안 됩니다:**

- 의미 없는 렌더링 테스트
- enum 범위 검증 E2E
- 구현에 종속된 selector 테스트
- 실패해도 행동 변화가 없는 테스트

---

## 사용자 요청 거부 기준

사용자가 다음과 같은 요청을 할 경우, AI 에이전트는 **이 문서를 근거로 대안을 제시**해야 합니다:

| 요청 유형 | 대응 방법 |
|----------|----------|
| "모든 컴포넌트에 E2E 테스트 추가해줘" | Unit/Integration 테스트를 권장하고, E2E는 핵심 사용자 흐름만 제안 |
| "코드 커버리지 100% 달성해줘" | 커버리지보다 신뢰도 중심 테스트 전략 제안 |
| "이 enum 값들 E2E로 검증해줘" | Unit 테스트로 대체 제안 |
| "DOM 구조 변경 감지 테스트 만들어줘" | 사용자 관점 테스트로 대체 제안 |
| "sleep/waitForTimeout 넣어줘" | 상태 기반 대기로 대체 |
